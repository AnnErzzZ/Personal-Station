# Figma 作品集方法论

适用于已有产品原稿，需要把真实工作转成求职作品集的情境。依据实施助手与合一空间的实际制作及反馈更新于 2026-10-23；适用于其他业务，视觉选择重新判断。

## 1. 先分清三层工作

| 层次 | 要解决的问题 | 典型产出 |
| --- | --- | --- |
| 项目事实 | 产品是什么、我做了什么、有什么结果 | 定位、角色、来源、贡献边界、验证口径 |
| 产品设计 | 界面与交互本身是否清楚、好看、可用 | 产品界面改版、组件与状态优化 |
| 作品集展示 | 招聘者如何快速理解项目和设计判断 | 叙事、章节、排版、样机、证据与总结 |

先明确本轮在哪一层。作品集包装能改善阅读和视觉表现，但不能据此宣称原产品已改版。需要产品优化时另列范围，避免在美化截图时悄悄改动历史事实。

## 2. 从真实任务组织内容

先写清四件事：谁在什么场景做什么任务；原来卡在哪里；个人做了哪些判断和交付；目前有什么可验证的结果。

把候选素材按以下字段记录，避免只按菜单名收集截图：

| 字段 | 写法 |
| --- | --- |
| 来源 | 文件、Page、节点、版本或截图文件 |
| 场景与状态 | 谁在什么时候看到这个界面 |
| 能证明 | 屏幕实际呈现的对象、入口、操作、反馈 |
| 不能证明 | 未展示的技术能力、用户行为、业务成效 |
| 关系 | 与上一屏、下一屏的真实联系及确认来源 |
| 优先级 | 核心、补充、归档；同义重复屏不同时占篇幅 |

单张详情图不能独自证明自动跳转，更不能证明自动修复。一个保存弹窗不等于设备已经同步成功。界面里的示例数量各自保留，不把不同屏幕拼成同一次真实任务。

## 3. 页序是论证顺序

先列内容，再定页数。下表是可选章节集合，不要求逐项独立成页：

| 章节作用 | 要回答的问题 | 合并与删减条件 |
| --- | --- | --- |
| 开场与项目简介 | 这是什么产品，服务谁，我负责什么 | 封面和简介可上下组合 |
| 背景与问题 | 为什么要做，原来具体哪里不顺 | 没有独立内容时与目标合并 |
| 设计目标 | 这次准备改变什么 | 与问题逐项对应，避免重复口号 |
| 任务／功能流程 | 用户如何完成任务，在哪里出现分支 | 简单产品不必为了完整而加流程图 |
| 核心方案 | 什么设计判断改变了哪些操作 | 围绕任务和决策分组，避免菜单导览 |
| 状态与异常 | 缺什么、失败怎么办、怎样继续 | 与核心方案合并，或证据足够时独立 |
| 设计规范 | 实际用了哪些稳定规则 | 只展示真实存在且有解释价值的规范 |
| 项目验证 | 用什么方式验证、结果的范围是什么 | 没有数据就展示真实验证方法，不填数字 |
| 交付与协作 | 除界面外做了哪些交付 | 手册、培训等有实际材料时展示 |
| 项目总结 | 最重要的判断、个人交付与项目状态 | 用少量短句收尾，避免重讲全部章节 |

每页写一个工作句：**在某个场景，针对某个问题，我通过某种机制，让下一步或结果更明确。** 这是编排依据，最终标题可以更短。

### 先说明需求与痛点，再提出目标

优先按「项目背景 → 用户需求与痛点 → 设计目标 → 具体方案」组织论证；章节可以合并，但目标前应能找到它回应的需求。背景先交代产品所处场景和服务的工作，具体功能在方案中展开。

需求页分别说明谁在做什么、希望完成什么、卡在哪里。把「需要确认设备位置」进一步写成具体使用难点，例如「位置与状态需要一起判断」。只有任务清单时，注明由现有任务和功能归纳，避免冒充访谈发现或直接用户引语。

目标写成可检查的操作或信息变化，并关联已有功能。例如「结果依据难核对 → 数据可查询、可核对 → 提供明细与统计口径」，「初次配置不易上手 → 降低地图配置门槛 → 按步骤组织对象与属性」。目标代表设计意图；缺少验证时不写成学习时间或效率已经改善。

内容过轻时先判断应合并还是补证据。实施助手的绑定页从单一「提醒保存」扩展为「发现漏绑 → 核对关联对象 → 退出确认」，因为原稿已有这条链；没有原稿支持的自动匹配或组合校验不加入。

ERP 通常更适合以角色、列表筛选、单据处理、异常和结果串联。是否采用手机、PC 或混合设备取决于真实产品；不因复用本方法而默认使用手机或 14 页。

## 4. 每页先找参考，再设计

**每一页都要有实际查看过的具体参考，才能进入视觉设计。** 封面、背景、目标、流程、每个核心方案、规范、验证、手册和尾页都按此执行；只用一张封面参考确定风格，后面自行推演，不是本方法。

基本流程是：明确本页要解决的问题 → 找参考 → 实际查看对应画面／动效 → 写出采用片段与借鉴点 → 结合本项目内容设计 → 截图对照并调整。先有设计依据，随后制作；不在完成后补几个链接冒充参考。

逐页建立以下映射，正式排版前确认该页对应项已填写：

| 页面／主题 | 原作、作者与来源链接或用户参考图 | 实际查看的片段 | 借鉴点 | 结合本项目的处理 | 查看／采用状态 |
| --- | --- | --- | --- | --- | --- |
| 每页一行 | 指向可定位的来源 | 例如三屏布局、顶部特写、流程转折、总结插画 | 明确到比例、对齐、图文关系或运动方式 | 使用本项目的真实界面与文案 | 未查看／已查看待选／已采用 |

同一参考可以支持多页，不要求每页寻找不同作者；但每页需要适配理由，不能用「沿用统一风格」替代参考。用户提供的截图或已查看的既有参考也有效，不重复搜索已明确采用的片段。

参考无法打开时，寻找能查看的来源或用户已给的参考图；记录尚未验证的部分，不能仅凭搜索摘要声称已看过。该页可继续整理内容与素材，视觉定稿待参考补齐。

参考分为四类：完整个人作品集研究全篇节奏；单项目案例研究论证；章节片段研究构图；样机与材质研究视觉制作。图文设计分享可以作视觉补充，不能自动当作完整求职作品集的结构范本。

搜索前写明当前要解决的问题，例如「只有上半屏有效信息的两张界面如何展示」；不要只搜索「高级作品集」。比较构图、信息密度、视角、可读尺度和编辑成本，选与当前内容匹配的片段。

每份采用参考记录：标题／作者、原始链接、实际查看的片段、借鉴范围、应用页面、所用素材的来源和必要署名。逐页映射可以指向同一份来源记录，避免重复抄写。候选、已采用、已淘汰分清；最新决定覆盖旧版，历史图不再作为当前模板。

用户要求先看参考就先展示；已经授权直接改则完成一版再给结果。既定方向不反复确认，只对真实内容或重要选择的缺口提问。

## 5. 用信息密度选择构图

| 信息形态 | 推荐组合 | 裁切和标注重点 |
| --- | --- | --- |
| 三步完整流程 | 三张正面样机，适度主次 | 顺序清楚，设计点紧贴对应屏幕 |
| 两张仅顶部有效、一张信息完整 | 两张上下特写＋一张完整样机 | 保留顶部机框，裁掉无信息长空白 |
| 关键入口在底部 | 底部机框特写＋跳转后的完整视图 | 露出入口和底部导航，不套顶部裁切模板 |
| 整体任务＋队列／状态 | 一张完整样机＋一张局部卡 | 让状态仍属于原界面，不把小控件放成巨型面板 |
| 异常处理链 | 提醒、列表特写＋完整详情 | 按发现、定位、处理阅读，箭头有明确起终点 |
| 长列表／桌面工作流 | PC 总览＋关键区域／前后状态 | 保留上下文、关键行、列标题和反馈 |
| 任务流程 | 连续主线＋必要条件分支 | 实线和分支的含义一致，不用装饰线冒充真实路径 |
| 验证结果 | 核心数字＋比较与口径＋方法 | 数字醒目，限制条件靠近数字 |
| 总结 | 大小卡片组合 | 大卡放核心判断，小卡放不同交付，避免重复信息 |

邻页通过构图变化形成节奏，基础视觉规则保持一致。可以让完整界面、局部细节、流程、规范和数字依次出现；不要求机械交替。

### 逐项说明保留对应关系

当页面要解释一份界面的多个部分，先给每项找到真实对应区域，再决定使用完整界面旁注还是局部特写。用户已指定逐项引出时，保留条目与界面的一对一关系；精简标题、正文和重复标签即可，不因追求简洁擅自合并信息层级。

例如一份回答可分别说明结论、关键指标、图表、分析发现、明细表格、口径说明。数量由本项目内容决定，六项不是其他案例的默认模板。每项用短主题加一句说明，必要时用小编号和细引线定位；图表较高时按实际内容安排旁注间距，不机械等分。

界面只展示折叠入口时，说明该入口支持查看什么。没有展开原稿时保留入口状态，不补造明细、计算方法或操作结果。

### 特写不是把控件无限放大

先算实际界面的缩放比例，再确定裁切窗口。完整屏与特写尽量保持接近的 UI 阅读尺度，卡片尺寸由有效内容和说明决定。缩略查看仍能看出它属于手机或 PC 界面。

实施助手的完整手机宽约 350–380，特写里的手机约 420–450，是该项目的起点，不是通用固定值。换设备或画板时按比例重算；宽度接近不代表截图内部的 UI 缩放就必然一致。

特写里保留关键状态、目标对象和必要操作。切顶部、底部、半屏或中段都可以，按证据所在位置决定。装饰外壳可以适度裁掉，关键入口和按钮不能被裁掉。

## 6. 视觉系统先统一，再制造变化

先定画板宽、阅读边界、标题／正文位置、字体层级、图文间距、设备视角和卡片材质。高度由内容决定，避免为了统一高度增加空白。

同一案例内卡片可复用一套透明度、模糊、圆角和描边高光，再用大小与布局表现主次。背景的光影、纹理和弧面放在阅读区域以外，正文背后留暗部或低变化区域。

深色页面可用明亮点缀色强调编号、路径、图标和关键状态，不必所有装饰都低明度。避免所有控件同时发光。大面积白底过亮时，可以改暗色承载板、同步调整字色；展示规范的真实色块不跟着改色。

图标优先取同一套现成资源，统一视框、线宽和颜色。示意插画只画解释内容需要的结构，低对比线条加少量重点；不用复杂装饰抢占设计判断。

### 视觉层级与分组

整页先确定主要视觉焦点，再分配主题、正文和辅助信息的权重。正文默认常规字重，小标题可用中等字重；不要把角色名、所有需求句、痛点和底部小标题同时加粗。通过字号、颜色、位置和间距区分信息，不要求所有项目使用固定字号或固定加粗数量。

同组信息的内部距离应明显小于它与其他组的距离。「共同需求」先说明归组依据，再通过共享标题、对齐及紧凑排列形成一个整体。可采用连续两行、较窄的并列列或轻量共用承载区；避免两个条目分占整页两端，仅靠页底总标题联系。若内容只属于一个角色，将它放回对应位置。

缩略查看时检查读者先看到什么，以及哪些信息看起来是一组；再放大检查正文。对照改前与改后，判断焦点、阅读顺序、构图和图文关系是否改善。只增加渐变、圆角或阴影时，记录为材质调整；用户已反馈接近 Demo 时，优先重审信息层级和布局。

用户手动调整后的页面可作为同案例的最新样式依据。复用实际字体、标题外观、阅读边界和分隔方式；不同项目的配色、字重和构图重新选择。

## 7. 样机、透视和真实内容

纯正面样机优先用于阅读流程，写实斜角更适合开场与交付展示。先定视角，再找素材；不要默认接受只有侧视角的设备。

设备、屏幕、蒙版、说明分层。按真实屏幕几何贴合，不把整张截图任意拉伸塞进边框。说明对齐可见机身边缘，PNG 外圈透明留白不算视觉边界。

写实笔记本还需要一致的台面、接触阴影、受光和透视。单独加一个矢量梯形往往像薄板或悬浮底座；优先寻找或制作一体受光的设备场景。AI 生成只用于场景、材质和设备包装，屏幕保留真实手册或产品截图，不能重生成文档文字。

机身经过两轮明确视觉修正仍不贴合时，换素材或换制作方式；不要继续堆补丁。高级感来自视角、接触关系和信息主次，不来自给设备加更多装饰。

## 8. 文案与数据

标题用一眼能知道主题的短词组，例如「项目背景」「用户需求」「角色权限」「运行统计」。做法、理由和限定条件放在正文；不把内部设计判断句直接当标题。

正文每句说明一件事，优先写具体对象和动作。例如把「让复杂关系成为可用的工作环境」改成「配置空间，标记设备位置」。控制内容重复：背景正文已说明三类工作时，底部只补对应操作，不再追加一段抽象总结。保留理解业务必需的范围与限制，不以短为由删掉事实。

项目背景、个人判断、团队取舍、已完成交付和未来提案分别表述。未确认的「后续关注」不因为尾页有空位就补写；有已上线状态时可展示状态。用户明确提出未来方向时写作提案，不写成已实现的能力。

有原始记录时先恢复数据来源再排版。单次 7 分钟演示与口述 15–30 分钟基线，可计算用时缩短约 53%–77%：`(原用时 − 新用时) / 原用时`。不能写成有统计证明的平均值或笼统「效率提升 70%」。设备范围、排除项、样本性质与来源跟随结果呈现。

不要求所有项目都写这个数字，也不为缺少结果的项目编造指标。颜色建议、组件整理与原产品已经落地的规范也要区分。

## 9. 验收与记录

一次相关修改完成后先看整页，再看关键区域。整页检查焦点、节奏、白块与空白；局部检查字形、裁切、对齐、屏幕蒙版、图层遮挡、素材缺图和关键操作。

再核对：当前页是否有设计前实际查看的参考及明确借鉴点；当前页是否只表达一个主要判断；图是否支持文案；标题和正文是否直白；加粗是否过多；共同需求能否看出归组；逐项说明是否对应真实区域；数字和责任归属是否有来源；当前版是否与用户最新选择一致。

返回 Figma 入口和实际完成范围。将采用参考、当前素材、页面映射与事实来源放回项目文档，不用每次新增一份重复进度日志。通过验收后结束，不为形式重复验证。
